把 FP8 搬到 RTX 3090（不需要 H100）

NVIDIA 讲 FP8 的故事通常是这样开场："想玩 FP8 数值，你至少得有一张 H100，或者一张支持 FP8 的极新 GPU，比如 RTX 4090。"

我不这么看。

换个说法：把 FP8 风格的数值实验回迁到 RTX 3090。

倒不是 Ampere 会自己算 FP8（它不会），也不是说这样能让 RTX 3090 比 Hopper 更快（不会）。而是因为 FP8 研究和工程的核心其实是：

  • 权重怎么存（线上跑时占多少字节）
  • 什么时候、在哪儿把它展开（decode）
  • 采用什么样的 scaling / 量化契约

只要愿意把 FP8 当成一种 存储格式，把数学运算映射到「实际能跑」的硬件上，消费级 Ampere 上可以覆盖其中相当大的一块。

顺便：看到不认识的缩写，去术语表翻一下。

代码：https://github.com/poad42/cuda-fp8-ampere

整体思路

Ampere（sm_86）的 tensor core 能力相当强，但没有原生 FP8 tensor-core MMA。它有的是：极快的 INT8 tensor core 通路（IMMA / WMMA）。

于是这个项目变成了：

把权重以 1 字节 FP8 位模式 存进 VRAM，运行时 decode / scale / 量化，然后用 INT8 tensor core 完成 matmul。

这就是全部思路：democratize FP8 研究——让「存储 + 数值」的实验能在大家真正手上的硬件上跑起来。

FP8-as-storage，一段话说完

不是在做「FP8 计算」。是把权重压成紧凑的 FP8 格式存着，需要的时候才展开。

VRAM 端很简单：FP16/BF16 权重 2 字节/权重，FP8 权重 1 字节/权重。所以大权重矩阵用 FP8 存，驻留权重占用和流带宽大致能砍一半（≈2×）。

实践里还得存 scale 因子（比如每个输出通道一个 FP16 scale），但相对完整的 $N\times K$ 权重矩阵这点开销可以忽略。

概念上：

  1. 权重以 FP8 字节（E4M3）存——就是 uint8 位模式；
  2. 用 256 项 LUT 把 FP8 → FP16 在线 decode；
  3. 按输出通道（per-column）乘 scale；
  4. 量化到 INT8，让 tensor core 能吃下；
  5. 跑 IMMA（INT8×INT8→INT32 累加），再写出 FP16 结果。

这就是「没有 FP8 MMA 也能玩 FP8」的全部。

哪些是新的（哪些不是）

先摆三条诚实的话：

  • 不是主张 Ampere 打赢 BF16/FP16 cuBLAS。纯算性能上，cuBLAS 通常很难被超越。
  • 不是完整的 FP8 训练。没有反向传播。
  • 本项目聚焦 FP8(E4M3) 存储。扩展到 E5M2 概念上类似（另一条 decode 通路），这次没做进文章里。

比特级 FP8 处理（LUT decode）

FP8 权重存成原始 uint8 位模式，用 256 项 LUT 解码。FP8 一共就 256 种字节，所以 decode 概念上就是：

  • u8 → fp16，走 LUT[u8]

这里没有 __byte_perm 之类的 trick——重点是让 decode 足够便宜，能藏进 tensor core 流水线后面。

scaling + 量化作为一等公民契约

权重不是"光有 FP8"这么简单，而是 FP8 位 + 每输出通道 scale。kernel 把这写死了：decode → 乘 scale → 饱和量化到 int8 → IMMA。

Stochastic Rounding（SR）：重要，但这里没实现

如果你在关心 FP8 训练动力学，SR 很关键。本项目没做 SR（没有反向传播），但要把这套搬到「类训练」实验上，SR 大概率会排在优先级前列。

术语表（速查）

  • FP8(E4M3)：8 位浮点格式，适合存，不适合高精度算。
  • MMA：矩阵乘加（tensor core 指令家族）。
  • IMMA / WMMA：NVIDIA int8 矩阵乘的 tensor core 通路（指令层 / CUDA API 层）。
  • cuBLAS / cuBLASLt：NVIDIA 的 GPU 线性代数库（GEMM）。
  • cp.async：Ampere 上的指令，异步从 global memory 拷到 shared memory。
  • l2pin：用 "persisting L2" 缓存提示让热张量在 L2 里多待一会儿。
  • Per-column scale：每个输出通道一个 scale；量化推理里常见。
  • LUT decode：FP8 一共 256 种位模式，decode 可以退化成查表。

Baseline：PyTorch decode + matmul

写自定义 kernel 之前，先要一个能对应真实工作流的 baseline：

# 权重以 FP8 字节存着
B_u8   = ...                # [N,K] uint8
# 每轮迭代把 fp8 -> fp16 解出来
B_fp16 = LUT[B_u8] * scales[:, None]
# 用标准 matmul 在 fp16 上算
out    = A @ B_fp16.T

这就是最朴素的 FP8-as-storage 实现：FP8 字节存着，按需 decode，然后交给 cuBLAS。

还有两个有用的额外 baseline：

  • decode + matmul + 输出降回 FP8：如果你还想让输出/激活也存 FP8，流水线长这样。
  • 只 matmul、fp16 权重常驻缓存：不是同一档（都不存 FP8 了），但能给出一个有用的上界。

Baseline 数字（PyTorch）

在 RTX 3090 Ti（sm_86）上测，CUDA 可见，形状 M=N=K=4096。

备注（重要，且容易被误读）：

  • "matmul only" 那条假设 fp16 权重已驻留——这正好抵消了 FP8 的 VRAM 收益。
  • "峰值分配" 指每轮调用内新分配的字节；不包含已常驻的 fp16 缓存权重。

朴素 decode+matmul 快不是悖论——cuBLAS 优化到极深，且 decode 一步天然可并行。写 fused kernel 的主要动机是控内存流量，以及把「权重存储 = FP8 字节」这件事从端到端做实。

熔进一个 kernel

一旦接受 IMMA 只吃 int8 fragment，剩下的全是流水线问题：

  • decode 在哪儿做？（constant memory LUT vs texture vs global）
  • scaling 在哪儿做？（fp16 里乘，还是烘进 int8 转换里）
  • 激活量化在哪儿做？（寄存器路径 vs shared-memory 中转）
  • 怎么让 tensor core 不空转？（避免被 decode/scale/quant 卡住）

实现上是先写一批变体用来证伪假设。

变体（实验项）

  • v2：baseline fused 通路（FP8→INT8 JIT + IMMA）。先简单，测数据。
  • v2_i8lut：「每列预生成 FP8→INT8 表放 shared memory 里，会怎样？」（听起来聪明；输了。）
  • v3_act_f16：融合激活量化，寄存器路径。
  • v4_act_f16：激活走 cp.async 中转 + shared-memory 量化，然后 IMMA。
  • texscale：per-column scale 走 TEX 读。
  • l2pin：对 B / scales 用 persisting-L2 提示。

那干嘛还要做？

看完两张表，最公平的问题就是：

朴素 Torch 都够快了，折腾干嘛？

因为「快」取决于你量的是什么。

纯 matmul 吞吐上，调得极狠的 fp16/bf16 GEMM 完全能赢。这个项目瞄准的是另一个约束：权重存储 + 权重搬运。

如果权重真以 FP8（1 字节/权重）存着，对比 fp16/bf16（2 字节/权重）你就是在冲 最多 2× 的权重流量削减 和 2× 的驻留权重占用削减。对内存受限的推理负载，这是实打实的杠杆——哪怕多花一点算力做 decode/scale/quant 也值。

具体到「democratize FP8 研究」这件事，好处是：

  • 存储格式可以保真（VRAM 里就是 FP8 字节）；
  • scaling/量化契约可以随便试；
  • decode/quant 的代价可以量出来，而不是被塞进预处理里看不见。

所以把它当成一个探索工具：端到端 FP8-as-storage，跑在官方不「支持 FP8」的硬件上。

自己动手

仓库：https://github.com/poad42/cuda-fp8-ampere

构建：

git submodule update --init --recursive
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

跑测试：

cd build
ctest --output-on-failure

跑 kernel 基准：

./build/gpu_bench --bench imma_fp8_jit_v2         --M 4096 --N 4096 --K 4096 --warmup 10 --iters 50
./build/gpu_bench --bench imma_fp8_jit_v2_l2pin   --M 4096 --N 4096 --K 4096 --warmup 10 --iters 50
./build/gpu_bench --bench imma_fp8_jit_v4_act_f16 --M 4096 --N 4096 --K 4096 --warmup 10 --iters 50

跑 Torch baseline（含端到端降 FP8）：

python scripts/bench_torch_vs_fp8imma.py --M 4096 --N 4096 --K 4096 --kChunk 32 --report_mem --downcast_out_fp8

下一步

如果再多给一个周末：

  • 加一个小小的数值正确性 harness（参考 decode + GEMM，带容差）。
  • 报一个更诚实的内存指标：驻留权重 + 峰值 workspace，而不只是 per-call 峰值分配。
  • 试更真实的形状（transformer 风格的 M、更大的 N、变化的 K），别只跑 4096³。

想深挖代码的话，仓库里有：

  • CUDA kernel 库（C++ API + C ABI）
  • 基准 harness（gpu_bench）
  • 一个极简 PyTorch 扩展
  • smoke tests（CTest + torch 编译/import 测试）
