定义与内涵编辑于 2026-04-10 12:44・北京 #

Harness Engineering（驾驭工程）是设计围绕 AI 代理（Agent）的系统、约束和反馈循环的学科，目的是使 AI 代理在生产环境中可靠运行。
一个"驾驭器"（Harness）不是代理本身，而是控制代理运作的完整基础设施：

  • 工具可访问性和权限管理
  • 保持代理安全的护栏
  • 帮助代理自我修正的反馈循环
  • 让人类监控代理行为的可观测层

马鞍与骑手的类比 #

术语借鉴自骑马装备。马匹强大且快速，但没有缰绳、马鞍和马嚼子，它会随意奔跑。

  • AI 模型 = 马匹（强大的动力源）
  • 驾驭器（Harness） = 所有将其力量引向生产用途的装备
  • 工程师 = 骑手（提供方向）


核心公式 #

Martin Fowler 简洁地定义：
Agent = Model + Harness
这个公式明确了：一个可靠的 AI 代理由两部分组成——模型本身（如 GPT-4、Claude 3）加上围绕它的驾驭系统。

Harness Engineering 解决的核心问题 #

没有驾驭器的 AI 代理只是一个演示原型，在受控环境中令人印象深刻，但在生产环境中会不可预测地失败。原因包括：

问题说明
无记忆状态原始模型在会话之间没有记忆。代理完成一个任务后开始另一个任务时，一切从零开始
自信的错误语言模型不会说"不知道"，而是产生看似合理但有时错误的输出
无边界工具访问没有护栏的代理可以删除文件、覆盖数据库或泄露凭证
规模乘数效应一个代理犯错可管理，但十个代理并行运行会产生级联故障

OpenAI Codex 团队的洞察 #

OpenAI Codex 团队直接描述了这一转变：
"软件工程团队的主要工作不再编写代码，而是设计环境、指定意图，并构建让代理能够可靠工作的反馈循环。"

AI Agent 的发展历程发布于 2026-04-10 12:50・北京 #

2024 年前：Prompt Engineering 时代

  • 专注于为单次模型调用设计有效输入
  • 简单的"输入 → 输出"模式
  • 适用于简单任务，但在复杂任务中失败率高

2025 年：Context Engineering 兴起

  • 开始关注上下文窗口管理
  • RAG（检索增强生成）成为主流
  • 代理开始使用工具和外部数据源

2026 年：Harness Engineering 时代

  • 系统级思考：不再关注单个提示，而是设计整个系统
  • 多会话协调：代理跨多个上下文窗口工作
  • 生产级可靠性：关注错误恢复、可观测性和护栏

为什么需要 Harness Engineering？ #

AI 模型的能力在飞速提升，但可靠性成为生产部署的最大障碍：

  1. 模型能力 vs 可靠性差距
    1. GPT-4 可以编写代码，但不能保证代码正确
    2. Claude 可以搜索网页，但不能保证结果准确
    3. 模型会产生幻觉、重复错误、陷入循环
  2. 生产环境的严苛要求
    1. 客户容忍度：99.9% 正确率 vs 模型的 70-80%
    2. 合规性：审计日志、权限控制、数据隐私
    3. 可观测性：可追溯的决策过程、错误诊断
  3. 多代理协作的复杂性
    1. 单个代理失败影响可控
    2. 十个代理并行运行，级联故障难以调试

OpenAI 发布 Codex，首个大规模生产级驾驭系统：

  • 超过 100 万行代码的应用程序，没有一行由人类编写
  • 团队平均每位工程师每天合并 3.5 个 PR

工具编排发布于 2026-04-10 13:03・北京 #

代理的能力由它可以访问的工具定义。工具编排包括：

  • 可用工具定义：哪些工具可用
  • 调用规范：如何调用
  • 权限配置：需要什么权限

工具类型示例：

工具类型示例权限需求
文件系统读取/写入文件目录级别限制
Shell 命令执行终端命令白名单模式
API 调用外部服务集成API 密钥管理
数据库查询SQL 执行只读/读写权限


护栏和安全约束 #

护栏是防止代理采取有害行动的确定性规则。它们在多个层面运作：

权限边界

  • 限制可访问的文件、目录或命令
  • 白名单/黑名单模式

验证检查

  • Linters：代码风格检查
  • 类型检查器：TypeScript, mypy
  • 测试套件：单元测试、集成测试

架构约束

  • 强制依赖边界
  • 命名约定
  • 模块隔离规则

速率限制

  • 防止无限循环
  • 标记使用预算控制

错误恢复和反馈循环 #

生产代理一定会失败。问题是它们是否能够优雅地失败。
错误恢复机制：

机制说明
自动重试升级策略（简单重试 → 退避 → 失败）
自我验证循环代理在提交前检查自己的工作
回滚机制恢复之前状态
循环检测识别代理陷入重复操作

实际案例：
LangChain 的编码代理仅通过改变驾驭器，在 Terminal Bench 2.0 上从 52.8% 跃升至 66.5%（前五名）。关键改进：

  • 添加自我验证循环
  • 添加循环检测

可观测性 #

无法改进无法观察的东西。可观测性意味着：

  • 记录每个代理操作
  • 跟踪令牌使用和成本
  • 记录决策点
  • 发现异常

关键问题示例：

  • 代理为什么选择这个工具？
  • 通过测试套件需要多少次尝试？
  • 代理在工作流程中花费最多令牌的地方在哪里？
  • 它最后一次需要人工干预是什么时候？

人工检查点 #

完全自主很少是合适的。驾驭工程包括设计何时以及如何咨询人类。
人工干预层级：

层级场景示例
显式批准门高风险操作"代理想运行 rm -rf。批准？"
定期审查检查点长期任务每 30 分钟审查进度
人工审查后备自动判断失败自动化测试失败，转交人工

前馈与反馈编辑于 2026-04-10 13:12・北京 #

Martin Fowler 提出了驾驭代理的两个关键控制方式：
前馈控制

  • 目的：预见代理行为并在行动前引导它
  • 作用：增加代理在第一次尝试中产生好结果的概率
  • 示例：
    • AGENTS.md 文件
    • Skills（技能定义）
    • 引导指令

反馈控制

  • 目的：在代理行动后观察并帮助其自我修正
  • 作用：在问题到达人类之前自我修正
  • 示例：
    • Linters（代码检查工具）
    • 测试套件
    • AI 代码审查

计算型 vs 推理型 #

计算型控制

特征说明
确定性结果可靠
速度毫秒到秒级
成本低
示例测试、linters、类型检查器、结构分析


推理型控制

特征说明
非确定性结果概率性
速度较慢（GPU/NPU 运行）
成本较高
示例语义分析、AI 代码审查、"LLM 作为评判者"

驾驭循环 #

人类的工作是通过迭代驾驭来引导代理。每当问题多次发生时，前馈和反馈控制应该改进，使问题在未来发生的概率降低甚至防止。

使用 AI 改进驾驭

编码代理现在可以以更低的成本构建更多自定义控制和自定义静态分析。代理可以帮助：

  • 编写结构化测试
  • 从观察模式生成规则草稿
  • 脚手架自定义 linters
  • 从代码库考古创建操作指南

质量左移 #

持续集成的团队一直面临挑战：根据成本、速度和关键性将测试、检查和人工审查分布在开发生命周期中。
时间分布建议：

时间点检查类型示例
集成前快速检查Linters、快速测试套件、基础代码审查代理
集成后昂贵检查变异测试、更广泛的代码审查
持续监控漂移检测死代码检测、测试覆盖率分析、依赖扫描

可驾驭性 #

并非每个代码库同样易于驾驭。
影响因素：

特性对驾驭的影响
强类型语言类型检查作为传感器自动可用
明确定义的模块边界架构约束规则可实施
框架抽象（如 Spring）隐藏细节，代理无需担心，增加成功概率


绿地 vs 棕地：

  • 绿地项目：可以从第一天开始构建可驾驭性
  • 棕地项目：特别是积累了大量技术债务的应用，面临更难的问题：驾驭器最需要的地方恰恰是最难构建的地方

OpenAI Codex编辑于 2026-04-10 13:25・北京 #

核心特性

  • AGENTS.md：机器可读的指令文件，告诉代理如何在仓库中工作
    • 运行哪些命令
    • 遵循哪些约定

  • CI 中的机械不变式：
    • 在每个边缘强制架构边界
    • 格式规则
    • 数据验证

Claude Code #

权限模型

  • 默认立场：只读，直到用户授予明确批准

Hooks 系统

允许用户在代理生命周期的关键点注入自定义脚本，启用：
