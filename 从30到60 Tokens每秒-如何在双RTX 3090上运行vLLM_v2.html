从 30 到 60 Tokens/秒：我如何让 vLLM 在双 RTX 3090 上跑起来

Linux / Ubuntu 下安装和使用 vLLM 的完整指南

Andrew Zhu 著 · 约 9 分钟阅读

事情是这样的。我用双 RTX 3090 跑 llama.cpp 已经好几个月了——能用，也挺稳定，就是慢。那种"等回复的功夫够泡杯咖啡"的慢。

Qwen3.6-27B，Q6 量化，大约 30 tokens/秒。聊聊天没问题，但如果你想让模型在午饭前帮你写完一篇长文，那就捉襟见肘了。

然后我发现了 vLLM。

经过一个周末与 Python 版本冲突死磕、清理残留 GPU 进程、甚至一度开始怀疑人生，我终于把它跑通了。结果是——60+ tokens/秒。速度翻倍，硬件没变。

这就是我的操作过程，也是为什么在多 GPU 环境下，vLLM 能把 llama.cpp 远远甩在身后的原因。

如果不想看原理分析、想直接上手安装，可以跳到第一步。

为什么 vLLM 比 llama.cpp 快？（真正的理由）

llama.cpp 确实出色——用 C/C++ 编写，可移植性强，从树莓派到 MacBook 通吃，在单 GPU、内存受限的场景里它依然是王者。但 vLLM 从设计之初就面向多 GPU 生产级服务，这种架构层面的差异，最终直接体现在性能数据上。

以下是 vLLM 真正跑得快的核心原因（尤其对于 Qwen3.6-27B 这类模型）：

一、CUDA Graphs：最关键的秘密武器

这是最重要的因素。vLLM 把整个前向传播预编译为 CUDA Graphs——本质上是把 kernel 启动序列录下来然后直接重放，彻底省去了 CPU 的调度开销。

  • llama.cpp：每生成一个 token 都要经历 CPU 到 GPU 的 kernel 启动、同步和内存管理，每个 token 增加约 1~2ms 的额外开销。
  • vLLM：整个解码步骤就是一次 CUDA Graph 重放，CPU 开销为零。

对于 27B 模型以 50 tok/s 的速度生成，每 token 1~2ms 的 CPU 开销累积起来占到了总延迟的 20%~40%。而 CUDA Graphs 直接把这部分消掉了。

二、Continuous Batching（连续批处理）：GPU 的空闲周期不是白给的

逐 token 生成时，GPU 大部分时间在空闲——它等着下一个 token 采样完。vLLM 把这些空闲时间塞给其他请求。

  • llama.cpp：请求按顺序或基础并行处理，解码阶段 GPU 利用率大约 30%~50%。
  • vLLM：在 token 级别交错处理多个请求，解码阶段 GPU 利用率可达 80%~100%。

一个用户？vLLM 稍快一点。三个用户？vLLM 吞吐量接近三倍，llama.cpp 就明显吃力了。

三、PagedAttention：彻底告别内存碎片化

vLLM 的 PagedAttention 以固定大小的块（类似操作系统的虚拟内存分页）来管理 KV Cache，消除了内存碎片，也让具有相似前缀的请求之间可以高效共享缓存。

  • llama.cpp：使用连续的 KV Cache 分配。长上下文 + 多请求 = 碎片化 + 浪费内存。
  • vLLM：基于块的分配，零碎片化。更好的内存利用率意味着每张 GPU 能容纳更长的上下文。

四、FlashAttention-3：更快的注意力计算

vLLM 内置 FlashAttention-3（也可用 FlashInfer），将注意力操作融合为更少、更高效的 kernel。llama.cpp 使用自己的注意力实现，性能不错但优化没有这么激进。

五、基于 NCCL 的张量并行

多 GPU 环境下，vLLM 使用 NCCL（NVIDIA 集合通信库）处理 GPU 间通信——经过大量实战验证，针对 PCIe/NVLink 做了深度优化，all-reduce 操作效率很高。

  • llama.cpp：更简单的层分割加手动 GPU 同步，能用但多 GPU 通信不够优化。
  • vLLM：基于 NCCL 的张量并行，配合优化的 all-reduce kernel。在双 RTX 3090（PCIe、无 NVLink）上，模型权重仍然可以实现接近线性的扩展。

测试场景llama.cpp (Q6)vLLM (AWQ INT4)原因

vLLM 更快，因为它是为吞吐量而生的，而非可移植性。CUDA Graphs 消除 CPU 开销，Continuous Batching 让 GPU 持续忙碌，FlashAttention 加速注意力计算，NCCL 高效地完成 GPU 间数据交换。

llama.cpp 的强项在于——把模型塞进有限的内存，以及在任何有 CPU 的设备上运行。

就我的使用场景来说——在消费级 GPU 上服务一个 27B 模型——vLLM 的吞吐量优势非常明显。速度翻倍，并发处理出色，而且提供与 OpenAI 兼容的 API，可以无缝接入任意客户端。

但也要提醒一句：vLLM 比 llama.cpp 占用更多显存。下面开始正式安装。

第一步：检查环境

安装之前，先确认系统环境就绪。

检查 GPU：

nvidia-smi

应该看到两块 RTX 3090，各 24GB 显存。如果报错，重装 NVIDIA 驱动：

# 或你需要的版本
sudo apt update
sudo apt install nvidia-driver-535
sudo reboot

检查 Python 版本：

python3 --version

vLLM 需要 Python 3.10~3.13。Python 3.14 太新了（截至 2026 年 5 月）。如果你在 3.14 上，可以：

  • 降级到 3.12：sudo apt install python3.12 python3.12-venv
  • 或者用 3.12 创建一个独立的虚拟环境

检查 CUDA 版本：

nvcc --version

需要 CUDA 11.8 或更高。RTX 3090 搭配 CUDA 12.x 效果最佳。

第二步：安装 vLLM（别走弯路）

你会看到很多教程建议你安装 uv（Astral 的快速 Python 包管理器）。但你并不需要它。普通的 Python venv 完全够用。uv 确实更快，但"够用"比"快但容易迷惑人"重要多了。

创建虚拟环境：

# 选择你的 Python 3.12 路径
python3.12 -m venv ~/vllm-venv
# 激活
source ~/vllm-venv/bin/activate

安装 vLLM：

pip install vllm

没错，就这一行。下载 PyTorch、CUDA 库和一系列 NVIDIA 依赖，大约 5~10 分钟。趁这个时间去泡杯咖啡。

验证安装：

python -c "import vllm; print(vllm.__version__)"
python -c "import torch; print(f'CUDA: {torch.cuda.is_available()}, Devices: {torch.cuda.device_count()}')"

你应该看到 vLLM 版本号，以及 CUDA: True, Devices: 2。

第三步：用小模型快速测试

加载 27B 模型之前，先用一个小模型验证一切正常。

python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-0.5B-Instruct \
  --host 0.0.0.0 \
  --port 8000

等待约 90 秒让模型加载编译完成，然后测试：

curl http://localhost:8000/v1/models

curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen/Qwen2.5-0.5B-Instruct",
    "messages": [{"role": "user", "content": "What is 2+2?"}],
    "max_tokens": 50
  }'

如果收到正常响应，说明 vLLM 工作正常。按 Ctrl+C 停止服务，接下来加载大模型。

第四步：vLLM 支持哪些模型格式？

在下载大模型之前，先搞清楚 vLLM 支持哪些模型权重格式。

格式说明示例模型
Hugging Face Safetensors标准 FP16/BF16 精度权重Qwen/Qwen3.6-27B
AWQ (INT4)4-bit 激活感知量化cyankiwi/Qwen3.6-27B-AWQ-INT4
GPTQ (INT4/INT8)4-bit 或 8-bit 量化TheBloke/Llama-2-7B-GPTQ
FP88-bit 浮点格式Qwen/Qwen3.6-27B-FP8

经验法则：只要模型在 Hugging Face 上，使用 Safetensors、AWQ、GPTQ 或 FP8 格式，vLLM 就能跑。如果是 GGUF 文件，那就得用 llama.cpp。

第五步：在双 RTX 3090 上运行 Qwen3.6-27B AWQ INT4

重头戏来了。让我们把 27B 参数模型加载到两张 GPU 上。

先下载模型：

# 安装 huggingface-cli
pip install huggingface_hub

# 下载到高速硬盘
huggingface-cli download cyankiwi/Qwen3.6-27B-AWQ-INT4 \
  --local-dir /mnt/data_2t/models/Qwen3.6-27B-AWQ-INT4

大约 20GB。网络好的话 15~30 分钟下完。

启动服务：

source ~/vllm-venv/bin/activate

python -m vllm.entrypoints.openai.api_server \
  --model /mnt/data_2t/models/Qwen3.6-27B-AWQ-INT4 \
  --served-model-name Qwen3.6-27B-AWQ-INT4 \
  --tensor-parallel-size 2 \
  --host 0.0.0.0 \
  --port 8000 \
  --max-model-len 131072 \
  --gpu-memory-utilization 0.95

各参数说明：

参数作用
--tensor-parallel-size 2将模型拆分到两张 GPU
--served-model-nameAPI 调用时使用的友好名称
--max-model-len 131072上下文窗口（128K tokens）
--gpu-memory-utilization 0.95使用 GPU 显存的 95%

首次启动大约需要 3 分钟。vLLM 会编译 CUDA Graphs 并缓存，之后启动会更快。

测试一下：

curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen3.6-27B-AWQ-INT4",
    "messages": [{"role": "user", "content": "Explain quantum computing in simple terms."}],
    "max_tokens": 200,
    "temperature": 0.7
  }'

你应该能看到 50~60 tokens/秒 的速度。同样的模型在 llama.cpp 上只有 30 tok/s。

第六步：FP8 KV Cache——更长的上下文，更少的显存

问题在于：KV Cache（模型对对话的"记忆"）非常吃显存。当上下文设为 262K 时，我的双 3090 就爆内存了。

解决方案：FP8 KV Cache。它把 KV Cache 从 16 位压缩到 8 位，内存占用大约减半。

格式vLLM 支持情况
GGUF❌ 不支持（llama.cpp 专用格式）
EXL2/EXL3通过 compressed-tensors 插件支持
Marlin支持 INT4

对于 RTX 3090，直接用 fp8 就好。原因：

  • fp8_e5m2 精度更好，但在 vLLM 中与 AWQ 量化模型存在兼容性问题。
  • fp8_e4m3 和 fp8 完全一样，只是名字不同。
  • 直接用 fp8 最省事，质量损失微乎其微。

启用 FP8 KV Cache：

python -m vllm.entrypoints.openai.api_server \
  --model /mnt/data_2t/models/Qwen3.6-27B-AWQ-INT4 \
  --served-model-name Qwen3.6-27B-AWQ-INT4 \
  --tensor-parallel-size 2 \
  --host 0.0.0.0 \
  --port 8000 \
  --max-model-len 202144 \
  --gpu-memory-utilization 0.95 \
  --kv-cache-dtype fp8

启用 FP8 KV Cache 后，202K 的上下文可以在双 RTX 3090 上正常运行。不启用的话，上限只能到约 130K。

第七步：速度测试——单用户 vs. 并发用户

用数据说话。以下是一个 Python 脚本，可以用来对当前环境进行基准测试：

import time
import requests

url = "http://localhost:8000/v1/chat/completions"
model = "Qwen3.6-27B-AWQ-INT4"

# 测试 1：短输入 → 短输出
print("=== 测试 1：短 → 短 ===")
start = time.time()
r = requests.post(url, json={{
    "model": model,
    "messages": [{{"role": "user", "content": "What is the capital of France?"}}],
    "max_tokens": 50
}})
elapsed = time.time() - start
d = r.json()
toks = d["usage"]["completion_tokens"]
print(f"{{toks}} tokens in {{elapsed:.2f}}s = {{toks/elapsed:.1f}} tok/s")

# 测试 2：长输入 → 长输出
print("\\n=== 测试 2：长 → 长 ===")
long_prompt = "Analyze this code: " + "def foo(): pass\\n" * 500
start = time.time()
r = requests.post(url, json={{
    "model": model,
    "messages": [{{"role": "user", "content": long_prompt}}],
    "max_tokens": 800
}})
elapsed = time.time() - start
d = r.json()
usage = d["usage"]
print(f"Input: {{usage['prompt_tokens']}} tokens")
print(f"Output: {{usage['completion_tokens']}} tokens in {{elapsed:.2f}}s")
print(f"Generation speed: {{usage['completion_tokens']/elapsed:.1f}} tok/s")

# 测试 3：Prefill（预填充）速度
print("\\n=== 测试 3: Prefill 速度 ===")
for size in [100, 500, 1000, 2000, 4000]:
    prompt = "Analyze: " + "def x(): pass\\n" * (size // 5)
    start = time.time()
    r = requests.post(url, json={{
        "model": model,
        "messages": [{{"role": "user", "content": prompt}}],
        "max_tokens": 20
    }})
    elapsed = time.time() - start
    d = r.json()
    input_tok = d["usage"]["prompt_tokens"]
    print(f"{{input_tok:5d}} input tokens → {{elapsed:.3f}}s (~{{input_tok/(elapsed*0.9):.0f}} tok/s prefill)")

作者实测结果（双 RTX 3090，Qwen3.6-27B AWQ INT4）：

测试场景结果
短输入 → 短输出（50 tokens）53.8 tok/s
长输入 → 长输出（800 tokens）51.8 tok/s
Prefill（4K tokens 输入）~1,418 tok/s
3 个并发请求145 tok/s 合计

vLLM 在这里表现突出。三个并发请求，每个生成 200 tokens：

  • 单请求速度：约 48 tok/s（因资源共享略降）
  • 总吞吐量：145 tok/s（接近单用户的三倍）
  • 实际耗时：三个请求都在约 4 秒内完成

这就是连续批处理的实际效果——GPU 始终保持忙碌，而不是在 token 之间空闲等待。

常见坑点（帮你少踩雷）

1. Python 3.14 不兼容

vLLM 需要 Python 3.10~3.13。如果你用的是全新 Ubuntu 26.04，自带 Python 3.14，那就用 3.12 创建一个虚拟环境。

2. 残留的 GPU 进程

Ctrl+C 不一定能杀掉 vLLM 的所有子进程，GPU 显存仍然被占用。解决方法：

pkill -f vllm
# 或者核弹选项：
fuser -k /dev/nvidia0 /dev/nvidia1

3. "KV Cache Memory Insufficient" 错误

遇到这个报错，可以：

  • 减小 --max-model-len 的值
  • 添加 --kv-cache-dtype fp8
  • 降低 --gpu-memory-utilization 到 0.90

4. 张量并行必须是 2 的幂

TP=1、2、4、8 可以工作，TP=3 会崩溃。如果你加了第三张 GPU，不如在上面跑另一个模型。

5. 首次启动很慢

vLLM 首次运行时会编译 CUDA Graphs（约 2 分钟），之后复用缓存，启动速度明显提升。耐心等待就好。

总结

vLLM 更快。 单用户场景下大约快两倍，多用户场景下差距进一步拉大。

llama.cpp 在以下场景仍然更优：需要 GGUF 支持、追求极致内存效率、或者想在特殊硬件（纯 CPU、Mac、边缘设备）上运行。

就我的使用场景——在消费级 GPU 上为个人和小团队服务一个 27B 模型——vLLM 是明确的选择。速度翻倍，并发吞吐出色，OpenAI 兼容的 API 可以接入任意客户端。

希望这篇指南能帮你搭建好自己的本地 AI 环境，让它跑得快快的。
