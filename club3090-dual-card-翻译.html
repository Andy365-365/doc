双卡 3090 — 加入第二张卡会改变什么

你拥有 2× RTX 3090。本页是双卡选型的入口：帮你决定用哪套配置，以及双卡相比单卡解锁了哪些能力。模型级别的深入内容（量化方案、Genesis 补丁、引擎内部实现）都在模型目录里——链接见文末。

你用的模型不在下面列出的配置中？或者想跑任意 HuggingFace 上的 safetensors 仓库？ → 看 docs/PULL.md：scripts/pull.sh 会根据 KV 计算评估任意模型（诚实评估，不下载），通过就直接启动。本页给出的配置都是实测过的路径；两条路都能走。

NVLink 自动检测（2026-05-14 起）：双卡 compose 现已自动检测 NVLink 桥接器是否就位。有桥就自动走 NVLink 优化路径，无桥则走 PCIe 模式。可在 .env 中通过 NVLINK_MODE=force_on|force_off 手动覆写。详见下文「NVLink 自动检测」一节。

有 3 张以上 GPU？ 看 MULTI_CARD.md——从 dual.yml 推导 TP=4 / TP=8 的配置、Qwen3.6-27B 的有效 TP 值（1, 2, 4, 5, 8, 10）、以及哪些能线性扩展、哪些不能。

经验法则：双卡环境下，优先上下文长度而非并发数

双卡 compose 的默认策略是 取 KV 池允许的最大上下文长度，同时将 --max-num-seqs 设为适度的上限（通常为 4）——而不是反过来。理由如下：

  • --max-num-seqs 是上限，不是预留。设为 4 并不会预留 4 倍上下文；它只是限制同时运行的请求数。短/中等请求仍然能装入共享 KV 池并发执行。
  • KV 池大小由显存决定，而非 --max-model-len。拉高上下文上限 不会 缩小池（例如 gemma-bf16-mtp 的池是 196,527 tokens，不论 --max-model-len 是 32K 还是 131K 都一样）。因此更高的上限对典型流量而言几乎零成本——它只允许单个请求变得更大，并不影响短请求的并发。
  • 双卡存在的意义就是解锁单卡做不到的事。2× 3090 的实际工作负载是一两个长上下文 agent，而非高 QPS 多租户。如果你要的是低上下文下的纯并发，单卡 compose 或副本是更合适的选择。

所以默认上限设得很高；仅在需要保证时才降低 --max-num-seqs（降到 2 或 1）——例如两个并发长上下文 agent 绝不允许互相抢占，或者单个长请求绝不允许被排队。compose 中记录了每个 slug 的梯度（gemma-int8-mtp: 98K/4 → 170K/2 → 262K/1；gemma-bf16-mtp: 131K 默认，降低 seqs 以保长上下文）。

⚠️ 唯一的例外是 vision。在接近最大上下文时加载大图片可能导致显存紧张的系统 OOM（例如 gemma-bf16-mtp 在 120K 单 stream 下仅剩 ~1.4 GB/卡 空闲）。对于 vision 密集型长上下文场景，降低 --max-num-seqs 或 --gpu-memory-utilization。典型上下文下的 vision 不受影响。

实测 TPS（2× 3090）

测试协议：每种配置 3 次预热 + 5 次实测的经典叙事和代码 prompt。底层环境：vLLM nightly 0.20.1rc1.dev16+g7a1eb8ac2 + Genesis v7.69 dev tip（commit 2db18df），RTX 3090 sm_86 PCIe-only @ 230 W。Cliff 2 在 TP=2 下不触发（DeltaNet GDN forward state 分布在两张卡上——dual.yml 上 237K 单 prompt 已验证）；v7.69 切换主要是 dual-turbo.yml 的卫生性提升（其旧 workspace_lock sidecar 现在被 Genesis PN34 环境门控覆盖）。逐配置运行详情 + 显存峰值：models/qwen3.6-27b/CHANGELOG.md。

显存预算（2× 24 GB, TP=2）

张量并行（TP=2）将权重和 KV 对称地分到两张卡上。每张卡持 ~7 GB 权重（对比单卡的 ~14 GB）加其份额的 KV 池。这就是双卡能解锁单卡做不到的原因：

  • 262K 上下文 + vision + 2 streams 在 dual.yml 下单卡约 23.6 GB（假设单卡则需 ~33 GB）
  • DFlash draft 增加 ~1.75 GB/卡（双卡可管理；单卡会挤占 KV）
  • 4 并发 stream 通过 dual-turbo 利用 TQ3 KV 的紧凑性，塞下 4 × 满上下文 KV 池

单卡情况，见 SINGLE_CARD.md。

选择配置

通用默认 — dual.yml

工作负载：什么都行。聊天、工具 agent、vision、多模态混合。2× 3090 的推荐默认配置。

🎯 不想手动指定 slug？ bash scripts/switch.sh qwen3.6-27b/default（或直接 bash scripts/launch.sh）会自动解析受推荐的双卡默认配置——在 2× 3090 上是 vllm/dual（ENGINE_PREFERENCE 中 dual 的顺序为 vllm > ik-llama > llama.cpp）。偏好其他配置（如多租户用 vllm/dual-turbo）？用 bash scripts/switch.sh --set-default vllm/dual-turbo 一次性锁定，之后裸启动直达该配置——见 FAQ。

262K 上下文，fp8 KV，MTP n=3，2 streams，vision tower 激活。有意不使用 Genesis——fp8 KV 不会触发驱动 Genesis 存在的 cudagraph bug（#40880），该 bug 是单卡的痛点。纯 vLLM nightly 路径。工具调用通过 --tool-call-parser qwen3_coder + --enable-auto-tool-choice 生效。全部 verify-stress.sh 检查通过。

何时选：显而易见的起点。除非下面某个专用变体正好对应你的工作负载，就选这个。强烈推荐用于 IDE 编码 agent（Cline / OpenCode / Roo / Claude Code / Cursor）——fp8 KV 避开了影响全部 4 种 TQ3-KV 变体的 inductor 编译路径泄漏。见 club-3090#16。

多租户 — dual-turbo.yml

工作负载：小团队或 agent 农场运行 2-4 个并发 session。Open WebUI 多用户、GitHub-Actions-with-AI-PRs 流程、批量 agent 运行。

262K + TurboQuant 3-bit KV + Genesis v7.69 PROD 环境变量栈 + 4 streams。TQ3 将每个 KV slot 压缩到 ~3 bits/token（对比 fp8 的 ~8 bits），这才使得 4 × 262K 池能塞进 2 张卡。KV 池 1.52M tokens，最大并发 4.67×。每 stream TPS 落在 58 narr / 76 code（n=5, CV 3-5%），AL 3.39-3.51，MTP 平均接受率 79-84%，显存 19.8 GB/卡。

并发吞吐量（n=4 streams，经典代码 prompt，2026-05-01 PM, vLLM v0.20 + Genesis v7.65 dev tip——v7.69 重测待定，但 decode TPS 阶段不受此次升级影响）：4 streams 聚合代码 TPS 269（对比单 stream 74 TPS 提升 3.63×），每 stream 均值 74（CV 3.1%）——真正的并行解码，非交织。逐运行详情见 results/v0.20-migration/dual-turbo-concurrent.summary。

⚠️ Decode-concurrent ≠ long-prefill-overlap（见 #208）。上面的 269 TPS 是decode-concurrent——N 个短 prompt streams 同时解码。一个不同的场景：一个长 prefill（大工具返回、文件读取、累积上下文）在另一个 stream 已经在解码时进入，可能将 decode 饿至 ~0.1–0.9 TPS 直至 prefill 完成：chunked-prefill 将重型 GDN/Mamba prefill chunk 与 decode token 合入同一 forward 步，且 align 块将 chunk 下限锚定在 1568 tokens，无法调为零。在 dual.yml（fp8）上观测到；这是混合模型架构层面的行为，所以任何双卡 chunked-prefill 配置都应预期同样的情况。因此请把 269 TPS 理解为聚合吞吐量，而非 agentic 流量下的延迟保证。缓解措施：降低 --max-num-batched-tokens 靠近 1568 下限以减轻（无法消除）；代理层准入控制——将大 prefill 与实时交互 decode 隔离——是真正的修复（--scheduling-policy priority 帮不上忙：它排准入顺序，不排 intra-step 计算）。逐 budget 延迟数据待社区 A/B 测试。

何时选：真正的并发负载。单用户在每 stream 曲线上感受不到收益——但此处 n=4 时的每 stream TPS 基本等于 n=1（74 vs 76 TPS code），所以作为单 stream 配置也可行（如果你要最大 KV 池）。只要可能服务 >1 个请求，或想要最大的等效单卡上下文，就选它。

常见陷阱（双卡专属）

Marlin pad-sub-tile-n 补丁（私有，自动应用）

双卡变体需要一个单文件补丁——我们对 vllm#40361 的 fork——用于 AutoRound W4A16 在 TP=2 下 output-dim 分片低于 64 的场景。补丁已在仓库中私有分发并自动挂载：每个双卡 compose 将 models/qwen3.6-27b/vllm/patches/vllm-marlin-pad/{marlin.py,MPLinearKernel.py} 以只读方式覆盖到原版 vLLM 镜像。无需克隆 vLLM 源码，无需额外设置——启动双卡变体的瞬间补丁已在位。上游 PR 合入后我们会移除覆盖层。

NVLink 自动检测

双卡 compose 自动检测是否安装了 NVLink 桥接器，并相应配置。无需单独的 compose 文件——dual.yml、dual-turbo.yml、dual-dflash.yml 和 dual-dflash-noviz.yml 均自动适配你的硬件。

工作原理：每个双卡 compose 挂载 scripts/detect_nvlink.sh 并在容器启动时在 entrypoint 中 source 它。脚本检查 nvidia-smi topo -m 中 GPU 间的 NVLink 链接，设置正确的 NCCL 环境变量，entrypoint 条件性地向 vLLM 传递 --disable-custom-all-reduce。

覆写：在 .env 中设置 NVLINK_MODE（传递到容器）：

  • auto（默认）——通过 nvidia-smi topo -m 检测
  • force_on——假设 NVLink 桥存在，启用 NVLink 模式
  • force_off——即使检测到 NVLink 也强制 PCIe-only 路径

无 NVLink 时，向 vLLM 传递 --disable-custom-all-reduce 并设置 NCCL_P2P_DISABLE=1。有 NVLink 时，启用 custom all-reduce，NCCL 走 NVLink 路径。双 3090 上每 stream TPS 差异约 10-15%（见 BENCHMARKS.md 中的跨配置数据）。

dual.yml 有意不使用 Genesis

单卡悬崖（Cliff 1 / Cliff 2）和驱动 Genesis 存在的 cudagraph bug（#40880）在 dual.yml 上不会触发——fp8 KV + 2 streams + 262K 有充足的余量。所以 dual.yml 运行纯 vLLM nightly，不带任何补丁树。如果你想在双卡上用 Genesis（如 dual-turbo 的 TQ3 spec-verify 路径），该变体已结构性地启用它，只是 dual.yml 本身不含 Genesis。

DFlash 变体强制 FP16 KV

DFlash 的 combine_hidden_states 路径需要 head_size=256 + non-causal，在 Ampere 上强制 FP16 KV——当前此路径没有 fp8 / TurboQuant 替代方案。追踪于 vllm#40334。该 PR 合入后即可去掉 --dtype bfloat16，让 dtype 自动检测。

DFlash 的 vision 兼容性

DFlash draft + ViT 路径有文档支持且可用（--language-model-only 历史上是必需的，现在可选）。dual-dflash.yml 保留 vision；dual-dflash-noviz.yml 舍弃它以换取额外 15K 上下文。

双卡上单用户 = 收益有限

如果单人在双卡上用，你为大部分单 stream 解码期间闲置在备用 GPU 上的硬件付了钱。收益体现在并发场景或需要 DFlash 时。对单用户而言，单卡往往更划算。

双卡支持的模型

  • Qwen3.6-27B——主要模型。单卡和双卡均可运行。量化方案（AutoRound INT4, GGUF Q3_K_XL / Q4_K_M）、Genesis 补丁范围（主要与单卡相关）、引擎内部实现，全部在模型目录中。
  • Gemma 4 31B——Ampere 24 GB 仅支持双卡（单卡启动即 OOM，8K 上下文也无法避免；需 32 GB+/卡）。两条 drafter 路径（MTP 通过 Google 官方 gemma-4-31B-it-assistant + DFlash 通过 z-lab）× 两种 KV 策略（bf16 / 32K vs INT8 PTH / 262K）+ AWQ-4bit-weights 变体。Genesis 不适用（Genesis 补丁是 Qwen3-Next 专属的）。

更多模型上线后，会在此列出对应的双卡 compose 集合。

提示：多模态与图像/视频模型在双卡上的注意事项

两条超出上述 LLM compose 的通用经验（接驳 Qwen3-Omni + 规划 2× 3090 上图像生成时学到的）：

  • 评估完整流水线的体积，而非仅 transformer。多模态和扩散模型捆绑了大型文本编码器（8–24 GB：T5-XXL、Qwen3-4B、Qwen3-VL-8B、Mistral-3-24B）。小量化 transformer 在加载编码器 + VAE + 激活后仍可能撑爆 24 GB 卡——因此图像模型通常无法与 LLM 共处一张卡。给它专用卡或分时复用（LLM 不运行时再跑它）。
  • 在单卡上通过 fp8/int8 KV 达到完整上下文，再考虑 TP/PP。在 PCIe 无 NVLink 环境下，张量/流水线并行需付逐层跨卡代价；将 KV 减半（fp8 / int8）往往能让模型以完整原生上下文落在单张卡上，零跨卡流量——在此场景下严格更优。（Qwen3-Omni 的 thinker 通过 fp8 KV 达到完整的 65K 单卡——无需 TP/PP。）
  • 图像/视频生成 → 在空闲卡上使用 ComfyUI，而非 LLM 栈。精选模型清单 + Open WebUI → ComfyUI UI 模式：FAQ.md → 图像与视频生成。
