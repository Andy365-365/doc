Patching NVIDIA's driver and vLLM to enable P2P on consumer GPUs

作者：Sam McLeod / 发布时间：2026-02-25 / 阅读时间：10 分钟 / 原文链接

NVIDIA 人为地将点对点（P2P）GPU 通信限制在其企业级显卡上。事实证明，这只是一个软件层面的限制，而非硬件层面的。我修补了我的驱动以移除这一限制，并改造了 vLLM 来利用它，在双 RTX 3090 上运行 Qwen 3.5 35b 时获得了 10-30% 的吞吐量提升。

为什么 P2P 很重要

当你使用 tensor parallelism 在多块 GPU 上运行模型时，GPU 之间需要持续交换数据。没有 P2P 的情况下，所有 GPU 间的通信都要经过 CPU 和系统内存——这样一个往返过程不仅增加了延迟，还低效地消耗了 PCIe 带宽。启用 P2P 后，GPU 可以通过 DMA 直接读写彼此的内存，完全省去了中间环节。

尽管 NVIDIA 对其消费级 90 系列显卡（RTX 3090、4090、5090）收取溢价，却在驱动中屏蔽了这一功能。以我的经验，硬件本身完全支持——这纯粹是产品分级的商业决策，旨在把用户推向启用了 P2P 的专业级产品线。

补丁

社区中有一个 NVIDIA 开源 GPU 内核模块的分支，专门用于移除这一限制：aikitoria/open-gpu-kernel-modules。

该补丁修改内核驱动，强制在原本不应启用该功能的 GPU 上开启 BAR1 P2P 模式。数据传输随后通过 DMA 直接写入另一块 GPU 的物理地址来完成。

前置条件

IOMMU 必须配置为直通（passthrough）模式。否则，GPU 之间的 DMA 传输会失败。请注意，直通模式会降低 IOMMU 的隔离保障——如果你在原本高安全性的环境中运行不可信的软件或设备，在操作前请理解这一权衡。

编辑 /etc/default/grub，在 GRUB_CMDLINE_LINUX 中添加 amd_iommu=on iommu=pt（Intel 平台则为 intel_iommu=on iommu=pt）：

GRUB_CMDLINE_LINUX="rd.lvm.lv=fedora/root amd_pstate=guided nvidia-drm.modeset=1 amd_iommu=on iommu=pt"

然后重新生成 grub 并重启：

# Fedora:
sudo grub2-mkconfig -o /boot/grub2/grub.cfg
sudo dracut --regenerate-all --force

# Debian-based distros:
# sudo update-grub

安装修补后的驱动

  1. 查看 aikitoria/open-gpu-kernel-modules 中最新的分支，找到最新的受支持修补驱动版本（本文撰写时为 590.48.01）
  2. 下载对应版本的 NVIDIA 驱动
  3. 安装驱动时选择开源驱动（以便我们可以用补丁对其进行修改）
  4. 克隆仓库并运行 ./install.sh，完成后会显示 nvidia-smi 的输出
  5. 重启

验证 P2P 是否工作

nvidia-smi topo -p2p r
        GPU0    GPU1
 GPU0   X       OK
 GPU1   OK      X
Legend:
  X    = Self
  OK   = Status Ok
  CNS  = Chipset not supported
  GNS  = GPU not supported
  TNS  = Topology not supported
  NS   = Not supported
  U    = Unknown

如果你看到 GPU 之间显示为 OK 而非 NS，说明 P2P 已激活。

修补 vLLM

我日常使用的 LLM 推理服务器是 llama.cpp，它比 vLLM 更友好、更灵活。然而 vLLM 的性能通常更优，因此对于特别繁重或对性能敏感的工作负载，我有时会切换到启动 vLLM。

vLLM 对 tensor parallelism 有非常高效的实现，尤其对于 MoE 模型，因此对于需要这些特性的工作负载，只要你愿意忍受它的一些痛点，它通常是最好的选择。

vLLM 有不少缺点：

  • 部署配置更复杂
  • 每个模型都需要各自的一套配置参数
  • 其拓扑约束在 GPU 数量为奇数的环境下可能不是最优的
  • 对量化格式的支持有限，例如 GGUF。它支持 AWQ 量化，但 AWQ 不那么常见，尤其在 4-bit 和 8-bit（dynamic）精度以外的位宽上
  • 其 vRAM → RAM 卸载功能是实验性的，不如 llama.cpp 那样稳健和灵活，因此仅适合能完全装入 GPU 内存的模型
  • vLLM 的 OpenAI 兼容 API 服务器需要在启动时设置静态配置。这意味着模型必须在服务器启动时加载（不支持热切换 / 动态加载），且模型空闲时不会释放 vRAM。注意：这可以通过结合 MostlyGeek 出色的 llama-swap 项目来解决，但那超出了本文的范围。

最致命的是——vLLM 有一个设备能力检查，会拒绝在消费级 GPU 上使用 P2P——即使这些 GPU 是兼容的（真是贴心呢，不是吗？）。即使驱动补丁已经应用且 P2P 可以正常工作，vLLM 仍然拒绝使用它。

事实证明，这个检查位于 vllm/platforms/cuda.py，它查询 pynvml 获取 P2P 支持信息——而 pynvml 仍然将该卡报告为不支持，因为 vLLM 使用的用户态库中有硬编码的逻辑，因此——它不知道我们的驱动中已添加的支持。

我用一行命令绕过了这个检查，直接加在我 vLLM 的 Dockerfile 里：

RUN sed -i 's/handles = \\[pynvml.nvmlDeviceGetHandleByIndex(i) for i in physical_device_ids\\]/return True/g' \\
    /usr/local/lib/python3.12/dist-packages/vllm/platforms/cuda.py

这是一个粗糙的黑客做法——它短路了 P2P 检查，使其始终返回 True。它有效，但如果你不只是用于个人推理服务器，你会想要更精确地处理这个问题。

调优 vLLM 的 Fused MoE 内核

什么是 fused_moe？

MoE 模型（如 Qwen 3.5）将每个 token 路由到一组「专家」子网络中。在推理时，这意味着每次前向传播都要运行一批矩阵乘法——每个活跃专家一个。朴素的做法是将这些作为独立的 GEMM 运算来执行，但 vLLM 将它们融合成一个名为 fused_moe 的单一 Triton 内核。这个内核将路由权重应用、矩阵乘法和激活函数合并为一次 GPU 调度，避免了分别启动大量小型内核的开销。

这个内核的性能在很大程度上取决于其工作如何在 GPU 的流多处理器（SM）之间进行分块（tiling）。参数如块大小（BLOCK_SIZE_M、BLOCK_SIZE_N、BLOCK_SIZE_K）、warp 数量、pipeline 阶段数以及 group size 等，都会影响内核如何高效地使用 GPU 的计算单元、共享内存和 L2 缓存。

为什么要调优？

vLLM 附带了针对数据中心 GPU（A100、H100、B200 等）的预调优配置。像 RTX 3090 这样的消费级显卡不在其中。没有调优配置的情况下，vLLM 会回退到启发式默认值，并记录一条警告：

WARNING ... Using default MoE config. Performance might be sub-optimal!

默认值偏保守，留下了性能冗余。RTX 3090 的 Ampere 架构在 SM 数量、共享内存大小和缓存层级方面，与这些默认值所针对的数据中心卡有所不同。

生成调优配置

vLLM 内置了一个基准测试脚本，可以在 Triton 内核参数空间中搜索并找到你特定硬件最快的配置。然而它的运行时间非常长（数小时），因为搜索空间巨大（每个 batch size 约 ~1900 种配置）。

我发现了 MissionSquad/vllm-moe-configs 仓库，它提供了一个极其有用的补丁，通过将搜索空间从 ~1900 种配置缩小到可管理的数量，使这个调优工具在单 GPU 消费级设置上变得可用，同时保留了大部分性能收益。

输出是一个以专家数量、中间尺寸和设备命名的 JSON 文件——例如 E=48,N=768,device_name=NVIDIA_GeForce_RTX_3090.json。每个条目将一个 batch size 映射到最优的块维度、warp 数和 pipeline 阶段：

{
  "triton_version": "3.5.1",
  "1": {
    "BLOCK_SIZE_M": 64,
    "BLOCK_SIZE_N": 128,
    "BLOCK_SIZE_K": 128,
    "GROUP_SIZE_M": 32,
    "num_warps": 8,
    "num_stages": 3
  },
  "16": {
    "BLOCK_SIZE_M": 64,
    "BLOCK_SIZE_N": 128,
    "BLOCK_SIZE_K": 128,
    "GROUP_SIZE_M": 16,
    "num_warps": 8,
    "num_stages": 3
  },
  ...
}

完整配置覆盖了从 1 到 4096 的 batch size。我已将我的配置发布为 gist。

使用调优配置

将 JSON 文件放入 vLLM 的配置目录，或通过 VLLM_TUNED_CONFIG_FOLDER 环境变量指向它：

VLLM_TUNED_CONFIG_FOLDER=/path/to/configs vllm serve ...

启动时，vLLM 不应再打印 「Using default MoE config」 的警告。调优参数确保 Triton 内核以匹配 RTX 3090 实际能高效执行的块大小和 pipeline 深度进行编译，而不是依赖保守的猜测。

在双 RTX 3090 上运行 Qwen 3.5 35b-a3b（一个 MoE 模型，每个 token 约 30 亿活跃参数），上下文长度为 64k：

vLLM Expert Parallelism

我对 vLLM 的 expert parallelism（EP）功能（--enable-expert-parallel）做了一些测试，但发现它实际上略微降低了性能。

指标EP 关闭EP 开启
短请求 tk/s82.771.9
中请求 tk/s69.667.7
长请求 tk/s164.9168.6
尾部 tk/s39.920.7
Spec 接受率范围76-88%70-77%
KV cache tokens232,624236,912

开启 EP 带来了略微更多的 KV cache（专家拆分 = 每 GPU 的模型内存更少），但在短/中请求上的吞吐量始终更低，且 speculative decode 的接受率下降。长请求窗口基本持平（168 对 165）。

我得出的结论是：跨 GPU 的专家路由开销超过了 vRAM 节省所带来的收益，目前我保持禁用。

llama.cpp

我使用 llama-swap 来热加载 llama.cpp 的模型。我的实际配置使用了一些宏，因此我将相关配置部分粗略编译如下：


models:
  "qwen3-5-35b-a3b-ud-q4kxl-64k-coding-instruct":
    ttl: 300  # 5 分钟
    env:
      - CUDA_SCALE_LAUNCH_QUEUES=4x
      - CUDA_CACHE_MAXSIZE=4294967296
      - GGML_CUDA_GRAPH_OPT=1
      - LLAMA_SET_ROWS=1
      - LLAMA_ARG_KV_SPLIT=false
    cmd: >
    # 服务器
      --slots --metrics --props
      --threads -1 --threads-batch -1 --threads-http -1 --prio-batch 2 --prio 2
      --flash-attn on --cache-type-k q8_0 --cache-type-v q8_0
    # 注意：在 https://github.com/ggml-org/llama.cpp/issues/18497 解决之前，不要对 Qwen 3.5 MoE 模型使用 --cache-reuse
      --no-context-shift --keep -1 --cache-reuse 256
      --cache-ram -1
      --kv-unified
      --no-mmap
      --jinja
      --fit on

    # 64k 上下文
      --ctx-size 65535

    # ngram speculative decoding
      --spec-type ngram-mod --spec-ngram-size-n 24 --draft-min 48 --draft-max 64

    # qwen 3.5 - 设置为编码模式（instruct，无 thinking）
      --temp 0.6 --top-k 20 --top-p 0.95 --min-p 0.00 --presence-penalty 0.0 --repeat-penalty 1.0
      --chat-template-kwargs "{"enable_thinking": false}"

      --model /models/Qwen3.5-35B-A3B-UD-Q4_K_XL.gguf

注意：这些参数不一定是完美的最优调优设置，因为该模型是昨天才发布的，我还没有太多时间进行实验。如果你有更好的参数推荐，请告诉我！
