1.1 从 Prompt Engineering 到 Harness Engineering #

AI Agent 工程方法经历了三次范式跃迁：

第一代：Prompt Engineering（2022-2024） 焦点在于优化单次 LLM 调用的输入提示。工程师通过精心设计的 System Prompt、Few-shot 示例、思维链（CoT）等技术提升模型输出质量。局限在于：每次调用是孤立的，无法处理长程任务、工具调用、状态管理等复杂场景。

第二代：Context Engineering（2024-2025） 焦点扩展到模型"看到什么"。包括 RAG（检索增强生成）、记忆系统、上下文窗口管理、动态上下文组装等。工程师开始意识到，模型的能力不仅取决于 Prompt，更取决于它获取的信息质量。

第三代：Harness Engineering（2025-至今） 焦点从"模型看到什么"跃迁到"模型在什么环境中工作"。Harness 是模型之外的整个执行环境——工具集成、记忆系统、约束机制、反馈循环、编排逻辑、可观测性管线。正如 deepset AI 所定义：Harness 是 Agent 可靠性的真正决定因素。

1.2 为什么 "Harness > Model" 成为 2026 年共识 #

2026 年初，多个关键事件推动了这一共识的形成：

OpenAI Codex 实践（2026 年 2 月）

OpenAI Harness 团队用 5 个月时间，3 名工程师完全通过 Codex 构建了一个百万行代码的内部工具，零人工编写代码。关键发现：当某件事失败时，修复方式从来不是"让模型更努力"，而是"什么能力缺失了？如何让它对 Agent 可见且可执行？"

Anthropic 三篇论文（2026 年 3-4 月）

  • Effective Harnesses for Long-Running Agents：Initializer Agent + Coding Agent 双 Agent 架构，解决多上下文窗口协作
  • Harness Design for Long-Running App Development：Planner + Generator + Evaluator 三 Agent 架构，实现多小时自主编码
  • Scaling Managed Agents：Brain / Hands / Session 三层解耦架构，p50 TTFT 降低 60%，p95 降低 90%+

LangChain 实验（2026 年 4 月）

LangChain 团队在 Terminal Bench 2.0 上固定模型（gpt-5.2-codex），仅修改 Harness 的 System Prompt、Tools 和 Middleware 三个旋钮，将得分从 52.8 提升到 66.5（+13.7 分），排名从第 30 名跃升至第 5 名。

LinkedIn 行业共识

Aashish Gupta 提出："2025 年是 Agent 之年，2026 年是 Harness 之年。新的护城河是 Agent Harness，不是模型质量。模型会持续改进，但真正的差异化在于你能多好地将它们 Harness 成可靠、可用、快速的东西。"

2.1 CAR 模型：Harness 层的学术分解 #

2026 年 3 月，学术界提出了 CAR 模型（Control, Agency, Runtime），将 Harness 层形式化分解为三个正交维度：

Control（控制层） 定义 Agent 的行为边界和决策规则。包括：

  • 约束机制（Constraints）：什么能做、什么不能做
  • 优先级规则（Priority Rules）：多个目标冲突时如何决策
  • 错误恢复策略（Error Recovery）：失败后如何回退或重试
  • 安全护栏（Safety Guardrails）：防止有害行为的硬约束

Agency（代理层） 定义 Agent 的自主行动能力。包括：

  • 工具调用（Tool Invocation）：Agent 可以调用哪些外部工具
  • 状态管理（State Management）：Agent 如何维护和管理自身状态
  • 决策逻辑（Decision Logic）：Agent 如何在多个行动中做选择
  • 子 Agent 委派（Sub-agent Delegation）：Agent 如何拆分任务并委派

Runtime（运行时层） 定义 Agent 的执行环境。包括：

  • 沙箱隔离（Sandbox Isolation）：Agent 代码执行的安全环境
  • 上下文窗口管理（Context Window Management）：如何管理有限的上下文
  • I/O 处理（I/O Processing）：输入输出格式化和验证
  • 可观测性（Observability）：Tracing、Logging、Metrics

CAR 模型的价值在于提供了一个分析框架，让研究者可以精确讨论 Harness 的哪个维度需要改进，而不是笼统地说"Harness 不够好"。

2.2 长程 Agent 的上下文窗口管理理论 #

长程 Agent 面临的核心挑战是：复杂任务无法在单个上下文窗口内完成，但每次新 Session 开始时 Agent 没有之前工作的记忆。Anthropic 的研究揭示了几个关键模式：

Context Anxiety（上下文焦虑）

Sonnet 4.5 等模型在接近上下文窗口限制时，会表现出"提前完成任务"的倾向——不是任务真的完成了，而是模型"感知"到上下文即将耗尽。Anthropic 的解决方案是在 Harness 中引入上下文重置机制，在适当时机主动重置上下文，同时通过结构化 Artifact 传递关键信息。

Progressive Disclosure（渐进式披露）

OpenAI Codex 团队发现，一个庞大的 AGENTS.md 文件会挤占任务、代码和相关文档的上下文空间。解决方案：将 AGENTS.md 作为目录（约 100 行），而非百科全书。Agent 在需要时按需加载相关信息。这是"渐进式披露"原则在 Agent 上下文管理中的应用。

Structured Artifact Handoff（结构化工件交接）

Anthropic 的 Long-Running Harness 使用 claude-progress.txt 文件 + Git 历史，让新 Session 的 Agent 能快速理解工作状态。每个 Session 结束时，Coding Agent 将当前进度、决策日志、下一步计划写入结构化文件，下一个 Session 的 Agent 读取这些文件后快速恢复上下文。

2.3 Meta-Benchmark 概念 #

传统 AI Benchmark 衡量的是"瓶中之脑"——在孤立环境或单一参考 Harness 下测试模型，然后将所有性能差异归因于模型本身。但 Harness Engineering 的兴起揭示了这个问题：

Benchmark 得分 = 模型能力 × Harness 质量，两者不可分离。

Meta-Benchmark 的核心思想是：使用一组标准化的基础 Harness（AGENTS.md、文档、Skills、Hooks），让不同模型在相同的 Harness 环境下竞争。这样 Benchmarks 才能真正衡量模型差异，而非 Harness 差异。
LinkedIn 上 Brett Taylor 提出："Meta-Benchmark 的想法：一组基础 Agent Harness 集合（AGENTS.md、文档、Skills、Hooks），封装非平凡应用。" 这为未来 Benchmark 设计提供了方向。

第三章：工业界核心实践发布于 2026-05-01 12:16・北京 #

3.1 OpenAI Codex：零人工代码的百万行代码库 #

背景

OpenAI Harness 团队进行了一项为期 5 个月的实验：完全通过 Codex 构建并交付一个内部工具，零人工编写代码。3 名人类工程师的日常工作从"写代码"转变为"设计 Harness"。

核心实践：

1.Repository Knowledge 作为系统记录

OpenAI 将代码仓库本身设计为 Agent 的"知识中心"，包含：

  • 设计文档目录：带验证状态和核心信念（Agent-first 操作原则）
  • 架构文档：领域和包层级的顶层地图
  • 质量文档：对产品每个领域和架构层打分，追踪差距
  • 计划系统：轻量级计划用于小改动，执行计划用于复杂工作，包含进度和决策日志
  • 技术债务追踪：活跃计划、完成计划、已知技术债务全部版本化并共置

2.Agent Legibility（Agent 可读性）

设计原则 当某件事失败时，修复方式从来不是"让模型更努力"，而是："什么能力缺失了？如何让它对 Agent 可见且可执行？"

具体实践：

  • AGENTS.md 作为目录（~100 行），而非百科全书——渐进式披露
  • 自定义 Linter 注入修复指令到 Agent 上下文
  • 每个业务领域有固定的层结构（Types → Config → Repo → Service → Runtime → UI）
  • 跨领域关注点（Auth、Connectors、Telemetry）通过单一显式接口（Providers）进入
  • 所有约束通过机械方式强制执行（自定义 Linter + 结构测试）

3.Agent 驱动的 PR 完成循环 Codex 被指示：

  1. 本地审查自己的改动
  2. 请求额外的特定 Agent 审查（本地 + 云端）
  3. 响应人类或 Agent 给出的反馈
  4. 循环迭代直到所有 Agent 审查者满意（Ralph Wiggum Loop）

关键启示

  • Harness Engineering 的核心不是"让模型更聪明"，而是"让环境更利于模型工作"
  • Repository 本身是 Agent 的"操作系统"——设计 Repository 就是设计 Agent 的工作环境
  • 约束不是限制，是倍增器：一旦编码完成，它们同时应用于所有地方

3.2 Anthropic Claude Agent SDK：三层解耦架构 #

背景

Anthropic 在长程 Agent Harness 设计上进行了系统探索，从 Initializer Agent + Coding Agent 的双 Agent 架构，演进到 Brain / Hands / Session 三层解耦的 Managed Agents 架构。

1. Initializer Agent + Coding Agent 双 Agent 架构

  • Initializer Agent：在首次运行时设置环境，将产品规格分解为任务列表
  • Coding Agent：一次实现一个功能，在每个 Session 结束时将 Artifact 传递给下一个 Session
  • claude-progress.txt：结构化进度文件，让新 Session 快速理解工作状态
  • Git 历史：作为版本控制和上下文传递的辅助手段

2.Planner + Generator + Evaluator 三 Agent 架构 在双 Agent 基础上增加：

  • Planner：制定整体计划
  • Generator：按 Sprint 实现功能（React + Vite + FastAPI + SQLite/PostgreSQL）
  • Evaluator：对输出进行质量评分，将主观判断转化为可量化的标准

3.Managed Agents：Brain / Hands / Session 三层解耦 这是 Anthropic 最重要的架构创新：

层职责关键设计
Brain（大脑）Claude 模型 + Harness 调用循环无状态，可随时启动/停止
Hands（双手）沙箱 + 工具执行环境按需通过 Tool Call provision，不提前等待
Session（会话）所有事件的 Append-Only 日志持久化、可查询、与 Brain 独立


性能提升：

  • p50 TTFT（Time to First Token）降低约 60%
  • p95 TTFT 降低超过 90%
  • 扩展到多个 Brain 只需启动多个无状态 Harness，按需连接 Hands

4.Context Anxiety 解决方案

Sonnet 4.5 在接近上下文限制时会"提前完成任务"。Anthropic 的解决方案：

  • 在 Harness 中引入上下文重置机制
  • 在重置前将关键信息写入结构化 Artifact
  • Opus 4.5 自身改善了这一问题，但 Harness 层面的防御仍然必要

3.3 LangChain：Harness 的 11 个旋钮 #

背景

LangChain 团队将 Agent Harness 视为一个有 11 个可调"旋钮"的系统，通过迭代改进循环（Run → Observe → Fix → Repeat）持续提升 Agent 性能。

Harness 的 11 个旋钮：

旋钮描述示例
System Prompt系统指令PreCompletionChecklistMiddleware 强制验证
Tools可用工具集工具选择、参数定义、错误处理
Middleware/Hooks模型和工具调用前后的钩子LocalContextMiddleware 注入环境上下文
Skills预定义的技能模块可复用的能力单元
Sub-agent Delegation子 Agent 委派策略何时委派、委派给谁
Memory Systems记忆系统短期记忆、长期记忆、向量检索
Reasoning Budget推理计算预算low/medium/high/xhigh 四级
Context Assembly上下文组装策略优先级排序、Token 预算分配、压缩
Verification验证机制Ralph Wiggum Loop 强制验证
Error Handling错误处理策略重试、降级、回退
Observability可观测性LangSmith 追踪、延迟、Token 计数、成本


关键实验结果：

  • 固定模型（gpt-5.2-codex），仅修改 System Prompt、Tools、Middleware 三个旋钮
  • Terminal Bench 2.0 得分从 52.8 提升到 66.5（+13.7 分）
  • 排名从第 30 名提升到第 5 名

核心方法论：迭代改进循环

Run Agent → Observe Failures → Classify → Fix Harness → Repeat

deepset AI 将其总结为："你不是在调试模型，你是在调试环境。"

PreCompletionChecklistMiddleware 实践：

  • 在 Agent 退出前拦截
  • 提醒 Agent 对照 Task Spec 运行验证
  • 类似 Ralph Wiggum Loop：一个 Hook 强制 Agent 在退出时继续执行

Reasoning Budget 优化：

  • gpt-5.2-codex 有 4 个推理模式：low / medium / high / xhigh
  • 高推理模式帮助规划，但消耗 2x Token/时间
  • Terminal Bench 的超时限制迫使 Harness 在推理质量和执行速度间做权衡

4.1 三层架构模型 #

Harness Engineering 的核心架构可以抽象为三层模型：

┌─────────────────────────────────────────────────────┐
│  Layer 3: Orchestration（编排层）                     │
│  工作流逻辑 · Agent 协调 · 路由决策 · 多 Agent 协作    │
├─────────────────────────────────────────────────────┤
│  Layer 2: Runtime Environment（运行时环境层）          │
│  工具集成 · 记忆系统 · 护栏 · I/O 处理 · 沙箱隔离      │
├─────────────────────────────────────────────────────┤
│  Layer 1: Model Interface（模型接口层）               │
│  API 调用 · Prompt 组装 · 响应解析 · Token 管理       │
└─────────────────────────────────────────────────────┘

L1：Model Interface（模型接口层）

  • API 调用管理（重试、限流、Fallback）
  • Prompt 组装（System Prompt + Context + User Query）
  • 响应解析（JSON Schema 验证、结构化输出）
  • Token 预算分配和压缩策略

L2：Runtime Environment（运行时环境层）

  • 工具集成（Tool Definition、参数验证、错误处理）
  • 记忆系统（短期记忆、长期记忆、向量检索）
  • 护栏（Guardrails：输入验证、输出过滤、权限控制）
  • I/O 处理（输入分类、输出格式化、格式验证）
  • 沙箱隔离（代码执行环境、文件系统隔离、网络隔离）

L3：Orchestration（编排层）

  • 工作流逻辑（DAG、状态机、事件驱动）
  • Agent 协调（多 Agent 通信、任务分配、结果聚合）
  • 路由决策（根据任务类型选择 Agent 或工具）
  • 错误恢复（重试、降级、回退策略）

4.2 Harness 核心组件详解 #

1.上下文组装管线（Context Assembly Pipeline）

输入 → [输入验证 + 分类]
        ↓
       [上下文检索]
        ├── 知识库（RAG）
        ├── 用户历史（Memory）
        ├── 系统规则（Guardrails）
        └── 动态数据（API 调用）
        ↓
       [上下文组装]
        ├── 优先级排序
        ├── Token 预算分配
        └── 压缩（如需要）
        ↓
       [Prompt 模板]
        ├── System Prompt
        ├── 组装后的上下文
        └── 用户查询
        ↓
       [模型调用]

OpenAI Codex 实践中的关键原则：

  • 渐进式披露：AGENTS.md 作为目录，按需加载详细信息
  • 优先级排序：与当前任务最相关的信息放在上下文最前面
  • Token 预算：为不同类型的上下文分配固定预算，防止溢出

2.工具集成与沙箱隔离

工具集成是 Harness 的核心能力之一。Open SWE 的实践提供了参考：

  • 工具数量限制：约 15 个工具（在 Harness 设计时强制，而非让 Agent 自由选择）
  • 工具定义标准化：每个工具有明确的输入/输出 Schema、错误码、重试策略
  • 沙箱隔离：每个任务一个隔离沙箱（Modal/Daytona/Runloop）
  • 权限最小化：Agent 只能访问完成任务所需的最小权限集

3.记忆与状态持久化

Anthropic 的 Managed Agents 架构将 Session（事件日志）独立为持久化层：

  • Append-Only Log：所有事件按时间顺序追加，不可修改
  • 可查询：Harness 可以查询历史事件，用于上下文重建
  • 与 Brain 独立：Session 不依赖特定的 Brain 实例，支持 Failover

LangChain 的记忆系统实践：

  • 短期记忆：当前 Session 内的对话历史
  • 长期记忆：跨 Session 的知识存储（向量数据库、知识图谱）
  • 工作记忆：当前任务的中间状态和进度

4.护栏与验证机制（Guardrails & Verification）

护栏是 Harness 中防止 Agent 行为失控的关键组件：

护栏类型功能实现方式
输入护栏验证输入合法性输入分类、格式验证、注入检测
输出护栏过滤有害输出内容过滤、格式验证、Schema 检查
行为护栏限制 Agent 行为工具权限、API 调用限制、时间/Token 上限
合规护栏确保合规性审计日志、PII 检测、法规检查


Ralph Wiggum Loop（OpenAI 提出）：

  • 一个 Hook 强制 Agent 在退出时继续执行验证
  • LangChain 的 PreCompletionChecklistMiddleware 实现了类似模式
  • 确保 Agent 不会"草草了事"

5.错误处理与重试逻辑
deepset AI 的方法论：

  1. 运行 Agent → 在真实任务上执行
  2. 观察失败 → 通过 Tracing 定位失败点
  3. 分类失败 → 归类为：工具失败、推理失败、上下文缺失、护栏过严等
  4. 修复 Harness → 针对特定失败类型更新 Harness
  5. 重复循环 → 每次循环消除一类失败模式

6.可观测性（Tracing & Monitoring）

Braintrust 提出的 AI Agent 评测框架将可观测性分为三层：

层级指标示例
推理层推理质量推理步骤数、推理深度、推理一致性
行动层行动质量工具调用成功率、行动正确率、行动效率
端到端任务完成任务完成率、完成时间、Token 成本

LangSmith（LangChain）提供：

  • 每个 Agent 行动的完整 Tracing
  • 延迟、Token 计数、成本指标
  • 生产到测试用例的一键转换

4.3 AI Engineering Maturity Matrix #

Hands-On Architects 提出的 Harness 成熟度模型将团队分为 5 个阶段：

阶段名称特征
Stage 0无 HarnessAgent 直接调用模型，无工具、无护栏、无可观测性

Brownfield 系统迁移路径：

  • Stage 0 → Stage 2：通常较直接
  • Stage 2 → Stage 3：需要团队整体投入，是最难的跃迁
  • Stage 3 → Stage 4：目前仅有少数团队达到

Brownfield 系统 Harness 就绪检查清单：

  1. 模块化：能否用一句话说明每个模块的职责？如果所有权模糊，Agent 会生成无处归属的代码。
  2. 边界执行：模块依赖是否显式且有方向？如果不是，Agent 会比人类更快地创建新的耦合。
  3. 测试覆盖率：Agent 能否在不依赖人工的情况下验证自己的改动？覆盖率的缺口就是 Agent 自主权的缺口。

6.5 AGENTS.md 规范与渐进式披露实践 #

AGENTS.md 已成为 Harness Engineering 的事实标准，但 OpenAI Codex 团队的实践揭示了关键原则：

反模式：AGENTS.md 作为百科全书

  • 一个庞大的 AGENTS.md 文件（500+ 行）
  • 包含所有规则、规范、约定
  • 结果：挤占任务和代码的上下文空间，Agent 要么忽略关键约束，要么优化错误的目标

最佳实践：AGENTS.md 作为目录

  • 约 100 行的目录文件
  • 指向更详细的文档（设计文档、架构文档、质量文档）
  • Agent 按需加载相关信息
  • 这是"渐进式披露"原则在 Agent 上下文管理中的应用

6.6 开源社区的最佳实践与反模式 #

最佳实践：

  1. 迭代改进循环：Run → Observe → Classify → Fix → Repeat
  2. 模块化设计：每个 Harness 组件可独立测试、替换、改进
  3. 渐进式披露：按需加载上下文，避免上下文过载
  4. 工具数量限制：约 15 个工具，在 Harness 设计时强制
  5. 沙箱隔离：每个任务一个隔离环境
  6. 结构化 Artifact：使用文件、日志、进度文件传递上下文
  7. 自动化验证：Ralph Wiggum Loop 强制验证

反模式：

  1. 巨型 Prompt：将所有逻辑塞入单个 Prompt
  2. 无限工具集：让 Agent 自由选择工具，缺乏约束
  3. 无隔离：多个任务共享同一环境
  4. 手动上下文管理：依赖人工管理上下文窗口
  5. 黑盒调试：无 Tracing、无日志、无可观测性
  6. 一次性 Harness：构建后不迭代改进

7.3 为什么 "Meta-Benchmark" 需要标准化 Harness #

传统 Benchmark 的问题在于：Benchmark 得分 = 模型能力 × Harness 质量。当不同团队使用不同 Harness 时，得分差异可能来自 Harness 而非模型。

Meta-Benchmark 的解决方案：

  • 使用一组标准化的基础 Harness（AGENTS.md、文档、Skills、Hooks）
  • 所有模型在相同的 Harness 环境下竞争
  • 这样 Benchmarks 才能真正衡量模型差异
