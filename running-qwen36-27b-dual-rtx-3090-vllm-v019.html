原文：Running Qwen3.6 27B Locally on Dual RTX 3090s with vLLM v0.19
作者：Derek Armstrong · 2026年4月26日 · 约 8 分钟阅读

在双 RTX 3090 上本地运行 Qwen3.6 27B —— vLLM v0.19 实战

本地跑一个前沿级别的模型，有一种云端订阅无法替代的满足感。Qwen3.6 发布后，我想在家庭实验室中以全能力运行它：160K 上下文、为 Cline 和 Roo Code 提供工具调用、投机解码，全都要。这篇文章覆盖了完整的过程：每一个配置决策、每一个报错、以及日志背后的真实含义。如果你也在消费级 Ampere GPU（RTX 3090、3080 等）上跑 vLLM，这里的大部分经验可以直接复用。

核心要点

  • 双 RTX 3090 可以在 160K 上下文窗口下，跑出可用于 Agent 编码的 Qwen3.6 27B AWQ-INT4 性能。
  • 最大的性能提升来自 FP8 KV Cache、FlashInfer Attention + Sampler，以及将 MTP 投机解码调至 1 个投机 Token。
  • vLLM v0.19 V1 的启动诊断严格但实用：大多数"神秘"的初始化崩溃，实际上都是显存没清理干净导致的。
  • 这套配置下批量吞吐量达到约 116~124 tok/s，相比之前基于 Ollama 的服务是大幅跃升。
  • 微小的配置细节也很关键。仅将 block size 从 32 改为 16，就回收了数百 MB 的 KV Cache 容量。

🎯 目标

我想要的不是一个跑分截图，而是一个能投入实际编码工作流的、接近生产环境的本地端点。这意味着：长上下文、稳定的工具调用解析、强大的多轮对话连贯性，以及足够的吞吐量——让 Cline 会话保持响应灵敏，而不是像在糖浆里对话。

🖥️ 硬件配置

  • 2x NVIDIA RTX 3090 24GB（共 48GB 显存）
  • AMD Ryzen 9 5950X
  • Unraid + Docker 容器

双 3090 是核心限制。它们是 sm86 架构（Ampere）：依然非常强大，但缺少一些新架构才有的特性。两张卡之间的 Tensor Parallelism 通过 PCIe + NCCL 通信，而非 NVLink 式的对称内存。能跑没问题，但存在额外开销。

🧠 模型：Qwen3.6 27B AWQ-INT4

Qwen3.6 27B 是一个稠密 Transformer，所有 270 亿参数在每次前向传播时全部激活。这与 35B-A3B 等 MoE 变体不同，而对于这个使用场景，这个区别至关重要。

在 Cline 和 Roo Code 的 Agent 编码场景中，模型需要在长上下文中追踪大量工具调用的结果，并持续输出可靠的 JSON。稠密架构在这方面往往是优势——每个 Token 都能动用全网络。MoE 通过每个 Token 只激活部分子网络来换取速度，但在复杂的会话中，可能会牺牲一些长程一致性。

本文使用的量化版本是 cyankiwi/Qwen3.6-27B-AWQ-INT4，一个 BF16-INT4 混合精度的 AWQ 模型，采用 compressed-tensors 格式。vLLM 在 Ampere 架构上可以直接通过 MarlinLinearKernel 运行它。

⚙️ 为什么选 vLLM v0.19

vLLM v0.19.1（2026年4月）默认使用 V1 引擎。V1 是一次重大的引擎重构：它将 EngineCore 独立出来，将分词、调度和流式输出与模型执行并行化，而不是串行处理整个流水线。实际效果是：同样的硬件上，吞吐量有了实质性的提升。

对于这个工作负载，两个 V1 特性尤为重要：

  • 零气泡异步调度——可与投机解码共存
  • 分段 CUDA Graphs——对 Qwen3.6 这种混合 Mamba/Attention 层的复杂模型架构更加友好

🧩 最终启动配置

python -m vllm.entrypoints.openai.api_server \
  --model cyankiwi/Qwen3.6-27B-AWQ-INT4 \
  --dtype bfloat16 \
  --quantization compressed-tensors \
  --kv-cache-dtype fp8 \
  --tensor-parallel-size 2 \
  --disable-custom-all-reduce \
  --gpu-memory-utilization 0.8349 \
  --max-model-len 160000 \
  --max-num-seqs 4 \
  --max-num-batched-tokens 16384 \
  --block-size 16 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --attention-backend FLASHINFER \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder \
  --reasoning-parser qwen3 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":1}' \
  --generation-config vllm \
  --trust-remote-code \
  --host 0.0.0.0 \
  --port 8000

环境变量：

VLLM_USE_FLASHINFER_SAMPLER=1

🔍 配置决策详解

--gpu-memory-utilization 0.8349

这个参数设置权重加载后，预留给 KV Cache 的显存比例。它不是动态的运行时上限——vLLM 在启动时进行内存分析，减去权重的占用，然后在这个上限下从剩余空间分配 KV Block。

48GB 总显存，权重约占 9.72GB（来自启动日志），0.8349 这个值让每张 GPU 分配到约 7.7GB 的 KV Cache 空间，总计约 118,400 个 KV Token。

这个精确到小数点后四位的值直接来自 vLLM 启动时的建议。v0.19 拥有更精确的 CUDA Graph 分析能力，日志建议从 0.83 提升到 0.8349，以维持等效的 KV 容量。

重要提醒：这假设容器启动时 GPU 是干净的。如果 Ollama、ComfyUI 或残留容器仍然占用着显存，V1 现在会在加载权重前校验可用显存，直接报错并给出清晰的提示。

--kv-cache-dtype fp8

FP8 KV Cache 相比 BF16 大约节省一半的 KV 内存——正是它让 48GB 显存跑 160K 上下文成为可能。日志中提到如果没有缩放因子可能会影响精度，但在这个工作负载中，实际精度损失可以忽略不计。

--tensor-parallel-size 2 + --disable-custom-all-reduce

模型切分到两张 GPU 上。禁用 custom all-reduce 强制使用 NCCL all-reduce，而非依赖 NVLink 的自定义内核。对于通过 PCIe 连接的 3090 来说，这是正确的选择。

--attention-backend FLASHINFER

FlashInfer（已包含在 vllm/vllm-openai:latest 镜像中）在该配置下，解码密集场景的性能优于默认的 FlashAttention2。配合 VLLM_USE_FLASHINFER_SAMPLER=1 环境变量，将 Attention 和 Sampling 都交给 FlashInfer 内核处理。

启动确认日志如下：

Using FlashInfer for top-p & top-k sampling.
Using AttentionBackendEnum.FLASHINFER backend.

MTP 投机解码配置

MTP 投机解码利用轻量级的草稿路径，在 Token 被接受时几乎"免费"获得额外输出。实际效果带来了可观的解码性能提升。

两个关键的实践选择：

  • "method":"mtp" 是 v0.19 的现代路径
  • 在量化设置下，num_speculative_tokens=1 的表现优于 2——因为接受率不足以证明额外的草稿计算是值得的

--block-size 16

Qwen3.6 的混合 Mamba/Attention 层对 Cache/Page 对齐非常敏感。在 block size 为 32 时，日志显示存在填充开销：

Add 3 padding layers, may waste at most 6.25% KV cache memory

降到 16 消除了这种浪费。在约 7.7GB 的 KV Cache 中，6.25% 就是约 480MB——在关心长上下文余量时，这不是一个可以四舍五入的数字。

前缀缓存 + 分块预填充

前缀缓存对于 Agent 会话至关重要——系统提示和代码上下文反复出现。一旦缓存，后续轮次就不用重新执行同样的重型预填充。

分块预填充防止大型预填充操作独占引擎，在多请求场景下保持延迟更稳定。

🐛 排查启动失败

有两个失败值得记录，因为它们乍一看都具有误导性。

失败 1：WorkerProc 初始化错误，实则是显存争用

第一次崩溃看起来像是 FlashInfer 兼容性问题：worker 进程在 init_device 阶段失败。但根本原因要简单得多——Ollama 还在每张 GPU 上占用着约 21.8GB 显存。

v0.19 的 V1 引擎在加载权重前会校验可用显存。每张 GPU 只剩约 1.74GB 可用，而需求约为 19.56GB，快速失败是预期行为。

解决方法：启动前先运行 nvidia-smi，确认两张 GPU 基本清空。在 Unraid 上，"空闲"不等于"释放了显存"——容器必须停掉。

失败 2：Docker 镜像选择

Unraid Community Apps 的模板指向了一个自定义的 qwen3_5-cu130 镜像，它早于 Qwen3.6 发布，可能不包含 FlashInfer。

应该使用：

vllm/vllm-openai:latest

使用过时的社区镜像，会产生看起来像后端兼容性问题、实则是打包问题的假象。

⏱️ 启动耗时分析：冷启动为何偏慢

冷启动大约需要 4~5 分钟。各阶段分解如下：

阶段耗时
模型权重加载（27B AWQ）~15.5s
草稿模型加载（MTP）~6.4s
torch.compile 主干~44.6s
torch.compile eagle head~7.2s
分析/预热运行~83.7s
CUDA Graph 捕获~1s
总计~144s

分析阶段的 shm_broadcast 警告在这个上下文中只是信息性的——通常是 worker 协调，等待 compile 完成。缓存预热后，重启会快得多，因为 /root/.cache/vllm/torch_compile_cache/ 会被复用。

📈 性能结果

吞吐量测试使用 2,000 Token 的生成任务。

测试并发数墙钟时间批量吞吐量单请求
Run 1234.2s116.9 tok/s58.5 tok/s
Run 2464.6s123.9 tok/s31.0 tok/s

观察：

  • 批量吞吐量随并发增加而提升（116.9 → 123.9 tok/s），说明 2 并发时 GPU 还有余量。
  • 之前看起来像"4 并发很慢"的行为，实际上是调度器的预期行为——由 --max-num-seqs 设得太低导致。
  • KV Cache 容量计算与实际行为吻合：真实的工具调用会话通常远低于 160K/请求，所以有效并发比最差情况建模要好得多。

作为对比，之前用 Ollama 在该硬件上跑 Qwen3.5 27B Q4_K_M 大概是 15~25 tok/s（单线程）。当前配置在实际工作负载中达到了约 5~7 倍的吞吐量提升。

🏗️ 混合架构笔记（Mamba + Attention）

Qwen3.6 混合了 Transformer Attention 和 Mamba 层。这就是你会看到 Mamba 特有的启动行为的原因： 

Mamba cache mode is set to 'align' for Qwen3_5ForConditionalGeneration
by default when prefix caching is enabled

Setting attention block size to 1600 tokens to ensure that
attention page size is >= mamba page size

align 模式让 Mamba 和 Attention 的 Page 在前缀缓存时保持一致。vLLM 会自动处理，但在调优 block size 和理解为什么某些值会产生不必要的填充开销时，了解这个背景很有帮助。

补充说明：这就是"能跑"和"跑得好"分道扬镳的地方之一。默认值已经不错，但看日志会更好。
