在双 RTX 3090 上用 vLLM v0.19 本地运行 Qwen3.6 27B

2026年4月26日 · Derek Armstrong · 阅读约 8 分钟

在本地跑一个前沿级别的模型，确实有一种云端订阅无法替代的满足感。Qwen3.6 发布之后，我就想把它完整地部署到家庭实验室里：160k 上下文、给 Cline 和 Roo Code 做工具调用、投机解码，全都要。

但我不想要那种粗浅的搭建方式——白白浪费性能。这篇 walkthrough 覆盖了完整流程：每一个配置决策、每一次报错、以及日志到底在说什么。如果你也在消费级 Ampere GPU（RTX 3090、3080 等）上跑 vLLM，这里大部分内容都可以直接参考。

核心要点

  • 双 RTX 3090 可以以 160k 上下文窗口运行 Qwen3.6 27B AWQ-INT4，达到可用的 agentic-coding 性能。
  • 最大的性能提升来自 FP8 KV Cache、FlashInfer attention 加 sampler，以及调优为 1 个投机 token 的 MTP 投机解码。
  • vLLM v0.19 V1 的启动诊断严格但实用：大部分"神秘"的初始化崩溃，本质上都是显存卫生问题。
  • 在这套配置下，批处理吞吐量达到了 116~124 tok/s，相比之前基于 Ollama 的部署是质的飞跃。
  • 小的配置细节影响很大。仅把 block size 从 32 改为 16，就收回了几百 MB 的 KV Cache 容量。

🎯 目标

我想要一个接近生产可用的本地端点，用于真实的编码工作流——不是跑个 benchmark 截图就完事。这意味着：长上下文、稳定的工具调用解析、强大的多轮一致性，以及足够的吞吐量，让 Cline 会话感觉响应灵敏，而不是像"对话糖浆"一样黏糊。

🖥️ 硬件

  • 2x NVIDIA RTX 3090 24GB（共 48GB 显存）
  • AMD Ryzen 9 5950X
  • Unraid + Docker 容器

双 3090 是最关键的约束。它们是 sm86（Ampere 架构）：依然非常强大，但缺少一些新架构才有的特性。两张卡之间的张量并行通过 PCIe + NCCL 通信，而非 NVLink 式的对称显存。能用，但有开销。

🧠 模型：Qwen3.6 27B AWQ-INT4

Qwen3.6 27B 是一个 dense transformer，所以每一次前向传播都会激活全部 270 亿参数。这与 35B-A3B 等 MoE 变体不同，而在这个使用场景下，这个区别很重要。

在 Cline 和 Roo Code 的 agentic 编码场景中，模型需要在长上下文中跟踪大量的工具调用结果，同时还能输出可靠的 JSON——dense 架构反而往往是优势。每个 token 都经过完整的网络。MoE 通过每个 token 只激活一部分参数来换取速度，但在复杂的会话中可能会牺牲一定的长程一致性。

这里使用的量化版本是 cyankiwi/Qwen3.6-27B-AWQ-INT4，一个 BF16-INT4 的 AWQ 模型，采用 compressed-tensors 格式。vLLM 可以直接通过 MarlinLinearKernel 在 Ampere 上运行它。

⚙️ 为什么选择 vLLM v0.19

vLLM v0.19.1（2026年4月）默认使用 V1 引擎。V1 是一次重大的引擎重构：它将 EngineCore 独立出来，将 tokenization、调度和 streaming 与模型执行重叠，而不是把整个流水线串行化。实际效果是在相同硬件上获得了实质性的吞吐量提升。

对于这个工作负载，V1 的两个特性尤为重要：

  • 零气泡异步调度——可以与投机解码共存
  • 分段 CUDA Graphs——对 Qwen3.6 这种混合 Mamba/attention 层的复杂模型架构特别有帮助

🧩 最终启动配置

vllm serve cyankiwi/Qwen3.6-27B-AWQ-INT4 \
  --dtype bfloat16 \
  --quantization compressed-tensors \
  --kv-cache-dtype fp8 \
  --tensor-parallel-size 2 \
  --disable-custom-all-reduce \
  --gpu-memory-utilization 0.8349 \
  --max-model-len 160000 \
  --max-num-seqs 4 \
  --max-num-batched-tokens 16384 \
  --block-size 16 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --attention-backend FLASHINFER \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder \
  --reasoning-parser qwen3 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":1}' \
  --generation-config vllm \
  --trust-remote-code \
  --host 0.0.0.0 \
  --port 8000

环境变量：

VLLM_USE_FLASHINFER_SAMPLER=1

🔍 配置决策详解

--gpu-memory-utilization 0.8349

这个参数设置的是权重加载后，预留给 KV Cache 的显存比例。它不是一个动态的运行时上限。vLLM 在启动时分析显存、减去权重占用的空间，然后在这个上限之下分配 KV blocks。

总显存 48GB，权重大约占用 9.72GB（根据启动日志），0.8349 这个值让每张 GPU 的 KV Cache 大约 7.7GB，总共约 118,400 个 KV tokens。

这个看起来很奇怪的 0.8349 直接来自 vLLM 启动时的建议。v0.19 有更精确的 CUDA Graph 分析，日志建议从 0.83 提升到 0.8349，以维持等效的有效 KV 容量。

重要提醒：这个前提假设容器启动时 GPU 是干净的。如果 Ollama、ComfyUI 或者残留的容器还占着显存，V1 会直接验证可用显存，不够就干脆报错，不会含糊。

--kv-cache-dtype fp8

FP8 KV Cache 相比 BF16 大约节省一半的 KV 显存——这正是 48GB 显存能跑 160k 上下文的关键。日志提到如果不配合 scaling factors 可能会影响精度，但在这个工作负载中，实际的精度损失微乎其微。

--tensor-parallel-size 2 + --disable-custom-all-reduce

模型切分到两张 GPU 上。禁用 custom all-reduce 后强制使用 NCCL all-reduce，而非依赖 NVLink 的 custom kernels。对于通过 PCIe 连接的 3090 来说，这是正确的选择。

--attention-backend FLASHINFER

FlashInfer（vllm/vllm-openai:latest 中已捆绑）在这个配置下，相比默认的 FlashAttention2 显著提升了 decode-heavy 场景的性能。配合 VLLM_USE_FLASHINFER_SAMPLER=1，将 attention 和 sampling 都切换到 FlashInfer kernels。

启动确认日志如下：

Using FlashInfer for top-p & top-k sampling.
Using AttentionBackendEnum.FLASHINFER backend.

--speculative-config '{"method":"mtp","num_speculative_tokens":1}'

MTP 投机解码使用一个轻量级的 draft 路径，当投机 token 被接受时，几乎是"白嫖"。在实际使用中带来了可观的 decode 性能提升。

两个关键的选择：

  • "method":"mtp" 是 v0.19 的现代路径
  • 在这个量化配置下 num_speculative_tokens=1 比 2 表现更好——因为 2 个投机 token 的接受率不足以弥补额外的 draft 计算开销

--block-size 16

Qwen3.6 的混合 Mamba/attention 层对 cache/page 对齐很敏感。block size 为 32 时，日志显示有 padding 开销：

Add 3 padding layers, may waste at most 6.25% KV cache memory

降到 16 就消除了这部分浪费。在大约 7.7GB 的 KV Cache 下，6.25% 就是大约 480MB——在关心长上下文余量的时候，这可不是四舍五入能忽略的。

--enable-prefix-caching + --enable-chunked-prefill

对于带有重复 system prompt 和代码上下文的 agentic 会话，prefix caching 效果显著。一旦缓存命中，重复的轮次就不用重新做同样的繁重 prefill。

chunked prefill 防止大型 prefill 操作独占引擎，在多请求场景下保持更稳定的延迟。

🐛 调试启动失败

有两个值得记录的失败案例——乍看都很有误导性。

失败 1：WorkerProc 初始化错误，本质是显存争抢

第一次崩溃看起来像是 FlashInfer 兼容性问题：worker process 在 init_device 阶段失败。但根本原因简单得多——Ollama 还在每张 GPU 上占着大约 21.8GB。

v0.19 的 V1 现在加载权重之前会验证可用显存。每张 GPU 只剩大约 1.74GB 可用，而需求大约是 19.56GB，fail-fast 是预期行为。

解决方法：启动前先跑 nvidia-smi，确认两张 GPU 基本干净。在 Unraid 上，"空闲"不等于"已释放显存"——容器必须停掉。

失败 2：Docker 镜像选择

Unraid Community Apps 模板指向一个自定义的 qwen3_5-cu130 镜像，这个镜像早于 Qwen3.6，可能不包含 FlashInfer。

应该使用：

vllm/vllm-openai:latest

使用过时的社区镜像，会导致看起来像后端兼容性问题，实际上只是打包版本不对。

⏱️ 启动耗时分析：为什么冷启动感觉慢

冷启动大约 4~5 分钟。拆解如下：

阶段耗时
模型权重加载（27B AWQ）~15.5s
Drafter 模型加载（MTP）~6.4s
torch.compile backbone~44.6s
torch.compile eagle head~7.2s
Profiling / warmup 运行~83.7s
CUDA Graph 捕获~1s
总计~144s

profiling 阶段出现的 shm_broadcast 警告在这个场景下只是信息提示——通常是 worker 协调等待 compile 完成。缓存预热之后，重启会快得多，因为 /root/.cache/vllm/torch_compile_cache/ 会被复用。

📈 性能结果

吞吐量测试使用 2000 token 的补全长度。

测试并发数墙钟时间批处理吞吐量单请求
Run 1234.2s116.9 tok/s58.5 tok/s
Run 2464.6s123.9 tok/s31.0 tok/s

观察：

  • 批处理吞吐量随并发数增加而上升（116.9 → 123.9 tok/s），说明 2 并发时 GPU 仍有剩余余量。
  • 之前看起来像"4 并发很慢"的行为，实际上是 --max-num-seqs 设置太低导致的调度预期行为。
  • KV Cache 容量计算与实际测量一致：真实的工具调用会话通常远低于 160k/请求，所以实际并发能力优于最坏情况的模型估算。

作为对比，之前在这套硬件上用 Ollama 跑 Qwen3.5 27B Q4_K_M，单线程大约 15~25 tok/s。这套配置在实际工作负载中达到了大约 5~7 倍的吞吐量。

🏗️ 混合架构笔记（Mamba + Attention）

Qwen3.6 混合了 transformer attention 和 Mamba 层。这就是你会看到 Mamba 特有的启动行为的原因：

Mamba cache mode is set to 'align' for Qwen3_5ForConditionalGeneration
by default when prefix caching is enabled

Setting attention block size to 1600 tokens to ensure that
attention page size is >= mamba page size

align 模式保持 Mamba 和 attention pages 在 prefix caching 下的对齐。vLLM 会自动处理这部分，但了解这些上下文对调优 block size、理解为什么某些值会产生不必要的 padding 开销很有帮助。

顺便说一句：这就是"能跑"和"跑得好"分道扬镳的地方之一。默认值已经不错，但看日志会更好。
